# Database Migrations (Alembic)

Schema changes are code: reviewed, tested and deployed like any other change. Table and constraint names follow the `db-naming-conventions` skill; security rules for database accounts are in `fastapi-security` §4.

## 0. Where things live

| What | Where |
|---|---|
| Models (source of truth) | `app/features/<feature>/models.py`; base and naming convention in `app/db/base.py` (generates `idx_`/`uq_`/`fk_`/`ck_` names) |
| Model registry | `app/db/models.py` imports every feature's models: **add new model modules here** or Alembic won't see them |
| Migrations | `migrations/versions/NNNN_<slug>.py` |
| Alembic config | `alembic.ini`, `migrations/env.py` (uses `DATABASE_URL`, `render_as_batch=True` for SQLite) |
| Run on startup | `AUTO_MIGRATE=true` → `app/db/migrate.py` runs `alembic upgrade head` |
| Seed / reference data | `app/features/rbac/service.py` (`sync_screens`, `ensure_roles`), run at startup, idempotent |
| Naming guard | `tests/platform/test_db_naming.py` |

## 1. Two phases of a project

**Template / pre-release (no real data anywhere yet):** keep a single `0001_initial_schema.py`. When the schema changes, delete it and regenerate (section 3), and move any local `data/app.db` aside. This keeps new projects free of migration history they never needed.

**Released (any environment holds data you care about):** never edit or delete a migration that has run anywhere. Every change is a **new** revision. From this point on, the rest of this document applies strictly.

Know which phase you are in before you touch `migrations/`. If unsure, assume released.

## 2. Workflow for a schema change

1. Change the model in `app/features/<feature>/models.py` (new module? register it in `app/db/models.py`). Name the table, columns and constraints per `db-naming-conventions`, and state the table category in the model docstring (`"""txn_: …"""`).
2. Generate the revision against a database that is at `head`:
   ```bash
   alembic upgrade head
   alembic revision --autogenerate -m "add txn_order" --rev-id 0002
   ```
   Use sequential four-digit `--rev-id`s (`0002`, `0003`…) and a short imperative message.
3. **Read and fix the generated file.** Autogenerate does not detect renames (it emits drop + add, which **loses data**), server defaults, some type changes, CHECK constraint edits, or data changes. Write those by hand.
4. Add a comment per new table with its category (`# txn_: transaction data`), as `0001` does.
5. Write a real `downgrade()` (section 6).
6. Verify (section 7), then commit the model, migration and tests together.

## 3. Regenerating the initial migration (template phase only)

```bash
rm migrations/versions/0001_initial_schema.py
DATABASE_URL=sqlite:////tmp/empty.db alembic revision --autogenerate -m "initial schema" --rev-id 0001
# add the category comments, then:
mv data/app.db data/app.db.bak   # the old local DB no longer matches
```

## 4. Rules for every migration

- **One logical change per revision.** Don't mix an unrelated index with a new table.
- **Explicit names everywhere.** Never rely on database-generated constraint names. The metadata naming convention handles this for autogenerated code; use `op.f("uq_…")` style names in hand-written code.
- **Portable SQL.** Migrations must run on SQLite (dev, tests) and the production engine. Use `op.*` operations and `sa.*` types. When raw SQL is unavoidable, branch on `op.get_bind().dialect.name`.
- **SQLite needs batch mode** for ALTERs: `with op.batch_alter_table("md_user") as batch: …` (already enabled for autogenerate).
- **New NOT NULL columns on existing tables:** add as nullable (or with a `server_default`), backfill, then make it NOT NULL in the same or a later revision. Never add a NOT NULL column without a default to a table that has rows.
- **Renames:** use `op.alter_column(..., new_column_name=...)` / `op.rename_table`, never drop + add. If indexes or constraints must be renamed on SQLite, recreate the table, copy the rows, and drop the old one in a single revision.
- **Data migrations** (backfills, splitting a column) go in their own revision. Use `op.execute(sa.text(...))` or lightweight `sa.table()` definitions inside the migration, never imports of current ORM models (they change later and break old migrations). Process big tables in batches.
- **No secrets or environment-specific data** in migrations. Reference/seed data that the app needs lives in idempotent startup code (`ensure_roles` style), not migrations, unless it must exist before the app can start.
- **Never** `DROP` a table or column that might hold data in the same deploy that stops using it (section 5).

## 5. Zero-downtime changes (expand → migrate → contract)

When old and new code run side by side during a deploy (rolling restarts, several replicas):

1. **Expand:** add the new column/table (nullable or defaulted); deploy code that writes both old and new.
2. **Migrate:** backfill existing rows; switch reads to the new structure.
3. **Contract:** in a later release, once nothing uses the old column, drop it.

Breaking a running version (renaming a column it still reads, dropping a table it still writes) is a production incident. If downtime is acceptable, say so explicitly and schedule a maintenance window instead.

## 6. Downgrades

- Every revision has a working `downgrade()` that restores the previous schema. If data cannot be restored (a dropped column), say so in a comment and raise in `downgrade()` rather than silently losing data.
- Downgrades are for recovering from a bad deploy quickly. For production data, the real safety net is the backup taken before migrating (section 8).

## 7. Verify before committing

```bash
# 1. fresh database builds from nothing
DATABASE_URL=sqlite:////tmp/fresh.db alembic upgrade head
# 2. models and migrations agree (no pending changes)
DATABASE_URL=sqlite:////tmp/fresh.db alembic check
# 3. down and up again (released phase)
DATABASE_URL=sqlite:////tmp/fresh.db alembic downgrade -1 && DATABASE_URL=sqlite:////tmp/fresh.db alembic upgrade head
# 4. on a COPY of real data when the change touches existing rows (SQLite: copy app.db and its -wal/-shm files)
# 5. the test suite (runs migrations on a temp DB) and the naming guard
pytest
```

Add `alembic upgrade head && alembic check` against a fresh database to CI so a model change without a migration fails the build.

## 8. Deploying migrations

- **Back up first.** Every production migration starts with a fresh, restorable backup (SQLite: `sqlite3 app.db ".backup app.db.bak"`; MySQL: `mysqldump --single-transaction`; PostgreSQL: `pg_dump -Fc`). Test restores periodically.
- **One migrator.** `AUTO_MIGRATE=true` is fine for a single container (it runs before the app serves traffic). With several workers or replicas, set `AUTO_MIGRATE=false` and run `alembic upgrade head` once as a separate deploy step (e.g. `docker compose run --rm app alembic upgrade head`) before restarting the app.
- **Separate credentials.** The migration step uses a DDL-capable database user; the running app uses a DML-only user (`fastapi-security` §4).
- **Long operations:** adding indexes or rewriting big tables can lock them. On MySQL use online DDL (`ALGORITHM=INPLACE, LOCK=NONE`) where supported; on PostgreSQL create indexes `CONCURRENTLY` (outside a transaction, via `op.execute` and `autocommit_block()`). Schedule anything that can't be online.
- **Never** run `alembic stamp` against production to "fix" a mismatch without understanding why it happened. It hides a missing schema change.

## 9. Switching engines

The default is SQLite (`data/app.db`). For MySQL or PostgreSQL: add the driver to `requirements.in` (`pymysql` or `psycopg[binary]`), recompile `requirements.txt`, and set `DATABASE_URL` (`mysql+pymysql://…?charset=utf8mb4`, `postgresql+psycopg://…`). Run the full verify list (section 7) against that engine before the first deploy. Differences show up in string length limits, case sensitivity, boolean storage, JSON support and DDL transactionality (MySQL commits DDL implicitly, so a failed migration can be half-applied: one change per revision matters even more).

## 10. Checklist

- [ ] Phase known (template: regenerate `0001`; released: new revision, never edit old ones).
- [ ] Names follow `db-naming-conventions`; category comment on each new table.
- [ ] Generated file reviewed: no accidental drop + add for renames, server defaults and constraints correct.
- [ ] NOT NULL additions are defaulted or backfilled; data migrations are separate and batched.
- [ ] `downgrade()` works, or the irreversibility is explicit.
- [ ] Fresh `upgrade head`, `alembic check` and `pytest` pass; tested on a copy of real data if rows change.
- [ ] Deploy plan: backup, single migrator, expand/contract if old code keeps running.
